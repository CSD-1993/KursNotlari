/*---------------------------------------------------------------------------------------------------------------------------
    Bu bölümde Rust'ta dosya işlemlerini ele alacağız. Rust'ta dosya işlemleri Rust standart kütüphanesindeki yapılarla 
    gerçekleştirilmektedir. Dosya işlemleri için sık başvurulan başvurulan türler şunlardır:

    ┌───────────┬─────────────────────────────────┬─────────────────────────────────────────┐
    │   Modül   │           işlevi                │               Temel Türler              │
    ├───────────┼─────────────────────────────────┼─────────────────────────────────────────┤
    │ std::path │ Yol ifadesinin temsili ve       │ Path, PathBuf, Component, OsStr         │
    │           │ manipülasyonu                   │ OsString                                │
    ├───────────┼─────────────────────────────────┼─────────────────────────────────────────┤
    │ std::fs   │ Dosya sistemi işlemleri (aç,    │ File, OpenOptions, Metadata,            │
    │           │ sil, kopyala vs.)               │ DirEntry, ReadDir                       │
    ├───────────┼─────────────────────────────────┼─────────────────────────────────────────┤
    │ std::io   │ Bayt tabanlı soyutlamalar ve    │ Read, Write, BufRead, Seek,             │
    │           │ hata ele alma modeli            │ BufReader, BufWriter, Error, ErrorKind  │
    └───────────┴─────────────────────────────────┴─────────────────────────────────────────┘

    Dosya işlemleri için dört ana tür vardır: File, Read, Write ve Seek. File bir yapıdır ve açık dosyayı temsil etmektedir. 
    Read ve Write ise birer trait'tir. File yapısı bu trait'leri desteklemektedir. Yani açık dosya üzerinde işlem yapmak için 
    Read ve Write trait'lerinden gelen metotlar kullanılmaktadır. Read ve Write trait'leri yalnızca File yapısı tarafından 
    değil dosya gibi işlem gören diğer yapılar tarafından da desteklenmektedir. Read ve Write trait'lerini destekleyen "dosya 
    gibi kullanılan" yapıların bazıları şunlardır:

    ┌────────────────────────────┬──────┬───────┬──────┬──────────────────────────────────────┐
    │            Tür             │ Read │ Write │ Seek │                 Açıklama             │
    ├────────────────────────────┼──────┼───────┼──────┼──────────────────────────────────────┤
    │ std::fs::File              │  +   │   +   │  +   │ Gerçek dosya (açılış moduna bağlı)   │
    │ std::net::TcpStream        │  +   │   +   │  -   │ TCP soketi                           │
    │ os::unix::net::UnixStream  │  +   │   +   │  -   │ Unix domain soketi                   │
    │ std::io::Stdin             │  +   │   -   │  -   │ Standart giriş                       │
    │ std::io::Stdout            │  -   │   +   │  -   │ Standart çıkış                       │
    │ std::io::Stderr            │  -   │   +   │  -   │ Standart hata çıkışı                 │
    │ Cursor<Vec<u8>>            │  +   │   +   │  +   │ Bellek içi tampon (test için ideal)  │
    │ Cursor<&mut [u8]>          │  +   │   +   │  +   │ Sabit boyutlu bellek tamponu         │
    │ &[u8]                      │  +   │   -   │  -   │ Byte dilimi (okudukça ilerler)       │
    │ &mut [u8]                  │  -   │   +   │  -   │ Değişebilir byte dilimi              │
    │ Vec<u8>                    │  -   │   +   │  -   │ Sona ekleyerek yazar                 │
    │ VecDeque<u8>               │  +   │   +   │  -   │ Rust 1.63+ (FIFO davranışı)          │
    │ BufReader<R>               │  +   │   -   │  +/- │ Tamponlu okuyucu                     │
    │ BufWriter<W>               │  -   │   +   │  +/- │ Tamponlu yazıcı                      │
    │ LineWriter<W>              │  -   │   +   │  -   │ Satır bazlı tamponlu yazıcı          │
    │ process::ChildStdin        │  -   │   +   │  -   │ Alt sürecin stdin borusu             │
    │ process::ChildStdout       │  +   │   -   │  -   │ Alt sürecin stdout borusu            │
    │ process::ChildStderr       │  +   │   -   │  -   │ Alt sürecin stderr borusu            │
    │ io::Empty (empty())        │  +   │   +   │  +   │ Boş akış (EOF döner, yazılanı yutar) │
    │ io::Sink (sink())          │  -   │   +   │  -   │ Her yazılanı yutan hedef             │
    │ io::Repeat (repeat(b))     │  +   │   -   │  -   │ Aynı byte'ı sonsuz döndürür          │
    └────────────────────────────┴──────┴───────┴──────┴──────────────────────────────────────┘

/*---------------------------------------------------------------------------------------------------------------------------
    Disk dosyaları std::fs::File yapısıyla temsil edilmektedir.dosya açmak için bu yapıdaki aşağıdaki ilişkli fonksiyonlar 
    kullanılmaktadır:

    pub fn open<P: AsRef<Path>>(path: P) -> Result<File>
    pub fn create<P: AsRef<Path>>(path: P) -> Result<File>
    pub fn create_new<P: AsRef<Path>>(path: P) -> Result<File>

    Bu fonksiyonların generic olduklarına dikkat ediniz. Fonksiyonların generic olmasının nedeni Rust'ya yol ifadelerinin
    (path names) değişik biçimlerde oluşturulabilmesindedir. Yol ifadeleri izleyen paragraflarda da ele alacağımız gibi 
    AsRef<Path> trait'ini destekleyen herhangi bir yapı türünden olabilmektedir. str türü ve String türleri de AsRef<Path>
    trait'ini desteklemektedir. 

    open fonksiyonu parametre olarak yol ifadesini alır, zaten var olan dosyayı açar. Eğer dosya yoksa fonksiyon başarısız
    olmaktadır. open fonksiyonu ile açılan dosyadan yalnızca okuma yapılabilir. create fonksiyonu "dosya varsa olanı sıfırlayarak 
    açar, dosya yoksa onu yaratır ve açar. create fonksiyonu ile açılan dosyalara yalnızca yazma yapılabilir. create_new 
    fonksiyonu var olmayan bir dosyayı yaratıp açar. eğer dosya varsa fonksiyon başarısız olmaktadır. Bu açım fonksiyonlarının
    C mod ve POSIX bayrak karşılıkları şöyledir:

    ┌─────────────────────────┬──────────────┬───────────────────────────────┐
    │     Rust Çağrısı        │ C fopen Modu │     POSIX open() Bayrakları   │
    ├─────────────────────────┼──────────────┼───────────────────────────────┤
    │ File::open(path)        │     "r"      │ O_RDONLY                      │
    │ File::create(path)      │     "w"      │ O_WRONLY | O_CREAT | O_TRUNC  │
    │ File::create_new(path)  │     "wx"     │ O_WRONLY | O_CREAT | O_EXCL   │
    └─────────────────────────┴──────────────┴───────────────────────────────┘

    Klasik C'de "exclusive" açım için bir yol yoktu. Bunun için C11'de "wx" modu da C'ye eklendi. 
    
    Yukarıdaki açım fonksiyonlarının yetersiz olduğunu fark etmişsinizdir. Örneğin "olanı bir dosyayı hem ondan okuma 
    yapmak hem de ona yazma yapmak için açmaya yönelik bir fonksiyon yoktur. Ancak bu işlemi yapmanın izleyen paragraflarda 
    açıklayacağımız gibi yolları vardır. 

    Yukarıdaki üç open fonksiyonun da geri dönüş değerine dikkat ediniz. Hepsi Result<Fle> türündendir. Rust'ta başarısız 
    olabilen fonksiyonların Option ya da Result enum türleriyle geri döndüğünü biliyoruz. Ancak std::result::Result türünün 
    iki generic parametresi vardır:

    pub enum Result<T, E> {
        Ok(T),
        Err(E),
    }

    Oysa buradaki Result türünün bir tane generic parametresi olduğuna dikkat ediniz. Bu generic parametre Ok durumunda 
    elde edilecek türü belirtmektedir. Buradaki Result türü Rust'ın temel std::result modülündeki Result türü değil 
    std::io modülündeki başka bir Result türüdür. std::io::Result türü şöyle tanılanmıştır:

    pub type Result<T> = Result<T, Error>;

    Buradaki tür tanımı C'deki typedef bildirimi gibidir. Yani std::io::Result<T> türü aslında std::result::Result<T, std::io::Error>
    ile eşdeğerdir. Yani bu Result türü Err varyantını std::io::Error türünden vermektedir. std::io::Error türü IO hataları 
    için oluşturulmu bir yapı belitmektedir. Bu yapının metotlarından IO hatası ile ilgili bilgiler alınabilmektedir. 
    Örneğin:

    let f: File = File::open("test.txt").unwrap();

    Bu örnekte eğer "test.txt" bulunamazsa open fonksiyonu Err varyantıyla geri dönecektir. unwrap metodu da Err varyantı 
    için panic uygulayacaktır. Tabii genellikle biz dosya açılamadıysa programı abnormal biçimde sonlandırmayız. Hata 
    kontrolü yaparak durumu ele alabiliriz. Örneğin:

    let f: File;

    f = match File::open("mest.txt") {
            Ok(f) => f,
            Err(e) => {
                eprintln!("{}", e);
                std::process::exit(1);
            }
    };

    Burada match deyiminin geri dönüş değeri f değişkenine atandığı için Err varyantında biz programı sonlandırmak zorunda 
    kaldık. Tabii kursumuzda "hataların ele alınması" kısmında da gördüğümüz gibi bu tür kontrollerin laternatif yoları da 
    vardır. Örneğin:

    let file: File;

    let result = File::open("test.txt");
    if result.is_err() {
        eprintln!("cannot open file!..\n");
        /* ... */
    }
    else {
        unsafe {
            file = result.unwrap_unchecked()
        }
    }

    Ya da örneğin:

    let f: File;

    f = File::open("test.txt").unwrap_or_else(|e| {
        eprintln!("cannot open file!...\n");
        std::process::exit(1);
    })

    Dosya işlemlerinde "test.txt" gibi göreli yol ifadelerinde orijin noktasının prosesin çalışma dizini (current working 
    directory) olduğunu anımsayınız. cargo programı ile "cargo run" yaparak programı çalıştırdığımızda prossin çalışma 
    dizini "cargo run" komutunun uygulandığı dizin olmaktadır. RustRover IDE'si ise prosesin çalışma diznini ana proje dizini 
    olarak set etmektedir. Maalesef "cargo run" komutunda prosesin çalışma dizinini ayarlamak için ek bir seçenek bulunmamaktadır. 
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    Biz bir dosyanın File yapısının open, create ve create_new isimli ilişkili fonksiyonlarıyla açıldığını ve açım sonrasında 
    bu fonksiyonların eğer başarılıysa Ok(File) değerini verdiğini söylemiştik. Ancak bu açım modlarının da yetersiz olduğundan 
    söz etmiştik. İşte dosyayı tam istenilen biçimde açabilmek için std::fs modülünde OpenOptions isimli bir yapı kullanılmaktadır. 
    Bu yapı kütüphanede demetsel biçimde tanımanmıştır. Ancak kullanıcının bu demetsel yapının alanlarını bilmesine gerek 
    yoktur. (Yapının private elemanlarına crate dışından erişemeyeceğimize göre onları bilmemizin de bir anlamı yoktur.) 
    Dokümantasyonda yapının alanları hakkında bilgi verilmemiştir:

    pub struct OpenOptions(/* private fields */);

    Bu yapı türünden bir değer yaratmak için yine yapının new ilişkili fonksiyonu bulunmaktadır. new ilişkili fonksiyonu 
    parametresizdir. Örneğin:

    let opop = OpenOptions::new();

    Biz erişemesek de yapının açış moduna ilişkin bayrakları tutan bir alanı vardır. Değer yeni yaratıldığında bu bayrakların 
    hiçbiri set edilmş değildir. 
 
    Yapının açış modlarına ilişkin bayrakları set eden metotları vardır:

    pub fn append(&mut self, append: bool) -> &mut Self;
    pub fn create(&mut self, create: bool) -> &mut Self;
    pub fn create_new(&mut self, create_new: bool) -> &mut Self;
    pub fn read(&mut self, read: bool) -> &mut Self;
    pub fn truncate(&mut self, truncate: bool) -> &mut Self;
    pub fn write(&mut self, write: bool) -> &mut Self;

    Bu metotlar bayrakların set m,i reset mi edileceğine ilişkin bool bir parametre alıp kendi nesnesinin referansına (adresine) 
    geri dönmektedir. Yani böylece bu metotların geri dönüş değerleri ile diğer metotları çağırabiliriz. Örneğin:

    let mut opop = OpenOptions::new();
    opop.read(true).write(true);

    Burada yeni bir OpenOptions değeri yaratılıp onun read ve write bayrakları set edilmiştir. Aşağıdaki kodu çalıştırıp 
    sonucu gözlemleyebilirsiniz:

    use std::fs::{OpenOptions, File};

    fn main() {
        let mut opop = OpenOptions::new();
        opop.read(true).write(true);

        println!("{:?}", opop);
    }

    Burada biz yalnızca bayrakları set edilmiş bir OpenOptions değeri elde ettik. İşte bu değeri kullanarak File değeri 
    oluşturabilmek için OpenOptions yapısının open metodu kullanılmaktadır. open metodunun parametrik yapısı şöyledir:

    pub fn open<P: AsRef<Path>>(&self, path: P) -> Result<File>

    Bu parametrik yapı File yapısının open ilişkili fonksiyonuna benzemektedir. Bu metot bu bayraklara uygun bir biçimde 
    File değeri oluşturmaktadır. Örneğin:

    let f: File = OpenOptions::new().read(true).write(true).open("test.txt").unwrap();

    Burada yaratılan OpenOptions değeri ifade sonunda drop edilecektir. Ancak artık open metodu bize başarı durumunda 
    açılmış olan dosyanın File değerine verecektir. 

    Yukarıdaki belirtmiş olduğumuz bazı bayraklar bazı bayraklarla birlikte kullanılamamaktadır. Hangi bayrakların hangi 
    bayraklar olmadan kullanılamayacağını aşağıda bir tablo halinde veriyoruz:

    ┌─────────────────────────────────┬──────────────────────┬─────────────────────────────────┐
    │          Kombinasyon            │        Sonuç         │             Açıklama            │
    ├─────────────────────────────────┼──────────────────────┼─────────────────────────────────┤
    │ truncate + (write/append yok)   │ InvalidInput hatası  │ truncate yazma erişimi ister    │
    │ create + (write/append yok)     │ InvalidInput hatası  │ create yazma erişimi ister      │
    │ create_new + (write/append yok) │ InvalidInput hatası  │ create_new yazma erişimi ister  │
    │ append + truncate               │ InvalidInput hatası  │ Semantik çelişki, her zaman     │
    │                                 │                      │ hata                            │
    │ create_new + create             │ Hata yok             │ create yok sayılır              │
    │ create_new + truncate           │ Hata yok             │ truncate yok sayılır            │
    │ Hiçbir erişim modu yok          │ InvalidInput hatası  │ read/write/append'ten en az     │
    │                                 │                      │ biri gerekli                    │
    └─────────────────────────────────┴──────────────────────┴─────────────────────────────────┘

    Rust'ın 1.58.0 (Ozak 2022) sürümüyle birlikte File yapısına options ilişkili fonksiyonu da eklenmiştir. Bu options 
    ilişkili fonksiyonu tamamen OpenOptions::new() işlemini yapmaktadır. Fonksiyonun parametrik yapısı şöyledir:

    pub fn options() -> OpenOptions
       
    Dolayısıyla artık ayrıntılı açış modları ile açım işlemi File yapısının sınırlarının dışına çıkmadan da gerçekleştirilebilmektedir. 
    Örneğin:

    let f: File = File::options().read(true).write(true).open("test.txt").unwrap();
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    File nesnesi yaratıldıktan sonra okuma ve yazma işlemleri File yapısının Read ve Write trait'lerinden gelen metotlar 
    tarafından gerçekleştirilmektedir. Bu noktada Read ve Write trait'lerinin metotları üzerinde duracağız. Önce Read trait'ini 
    ele alalım. 

    Read trait'inin metotları şunlardır:

    pub trait Read {
        // Required method
        fn read(&mut self, buf: &mut [u8]) -> Result<usize>;

        // Provided methods
        fn read_vectored(&mut self, bufs: &mut [IoSliceMut<'_>]) -> Result<usize> { ... }
        fn is_read_vectored(&self) -> bool { ... }
        fn read_to_end(&mut self, buf: &mut Vec<u8>) -> Result<usize> { ... }
        fn read_to_string(&mut self, buf: &mut String) -> Result<usize> { ... }
        fn read_exact(&mut self, buf: &mut [u8]) -> Result<()> { ... }
        fn read_buf(&mut self, buf: BorrowedCursor<'_>) -> Result<()> { ... }
        fn read_buf_exact(&mut self, cursor: BorrowedCursor<'_>) -> Result<()> { ... }
        fn by_ref(&mut self) -> &mut Self
        where Self: Sized { ... }
        fn bytes(self) -> Bytes<Self> 
        where Self: Sized { ... }
        fn chain<R: Read>(self, next: R) -> Chain<Self, R> 
        where Self: Sized { ... }
        fn take(self, limit: u64) -> Take<Self> 
        where Self: Sized { ... }
        fn read_array<const N: usize>(&mut self) -> Result<[u8; N]>
        where Self: Sized { ... }
    }

    Görüldüğü gibi trait'in tek bir zorunlu (required) metodu vardır:

    fn read(&mut self, buf: &mut [u8]) -> Result<usize>;

    Yani bu trait'i destekleyen türler yalnızca bu metodu yazmak zorundadır. Trait'in diğer metotları bu read metodu kullanılarak
    yazılmıştır. 

    read metodunun &mut self dışındaki parametresi (buf parametresi) u8 türünden bir dilim referansı almaktadır. Dilim referanslarının
    kendi içerisinde gösterici ve uzunluktan oluşan iki parçaya sahip olduğunu anımsayınız. İşte read metodu bu dilim referansındaki
    uzunluk kadar dosyadan okuma yapmaya çalışmaktadır. Metot dosya göstericisinin gösterdiği yerden itibaren dosya sonuna 
    kadar talep edilen miktarda okuma yapamazsa okuyabildiği kadar okuma yapar ve okuyabildiği byte sayısına geri döner. 
    Dosya göstericisi dosyanın sonundaysa metot hiç okuma yapamaz ve 0 ile geri döner. Metot IO hatası ya da erişim hakları 
    nedeniyle başarısız olursa std::io::Error değeriyle geri dönmektedir. Örneğin:

    use std::io::{Read};
    use std::fs::{File};

    fn main() {
        let mut f: File = File::open("test.txt").unwrap_or_else(|err| {
            eprintln!("ERROR: {}", err);
            std::process::exit(1);
        });

        let mut buf = [0u8; 10];
        let size: usize;

        size = f.read(&mut buf).expect("cannot read file!..");
        println!("{} bytes read: {:?}", size, buf);
    }
    Burada dosyadan 10 byte okup ekrana yazdırılmıştır. Biz open fonksiyonunda dosya açılamadıysa neden açılamadığına 
    yönelik bir hata mesajını stderr dosyasına yazdırdık, ancak read metodunda doğrudan expect uyguladık. Burada da benzer 
    kontrolü yapabilirdik. Yukarıdaki kodda biz diziye ilkdeğer vermek zorunda kaldık. Çünkü Rust'ta bir değişkeni kullanmadan 
    önce (adresini alma işlemi de dahil olmak üzere) ona ilkdeğerin verilmesi zorunludur. Bu durum C'den geçenlerde biraz 
    tuhaf gelebilmektedir. (Yani "zaten ben o dizinin içeriğini bozacağım, neden ona ilkdeğer vermek zorunda kalıyorum" 
    sorusu makuldur.) unsafe blok kullanmadan Rust'ta bundna kurtulmanın iyi bir yolu yoktur. Ancak unsafe blok içerisinde 
    daha önce görmüş olduğumuz MaybeUninit türünü kullanabiliriz:

    let mut buf: [u8; 10] = unsafe { std::mem::MaybeUninit::uninit().assume_init() };

    Ancak bu onuyu ele alırken belrttiğimiz gibi Rust'ta unsafe özelliklerin mümkün olduğunca kullanılmaması önerilmektedir. 

    read metodunun byte düzeyinde okuma yaptığına dikkat ediniz. Eğer okduğunuz byte'lar Unicode UTF-8 kodlamasına ilişkin 
    yazılardan oluşuyorsa ondan String yapısının from_utf8_lossy ilişkili fonksiyonu ile String elde edebilirsiniz. Örneğin:

    size = f.read(&mut buf).expect("cannot read file!..");
    let s = String::from_utf8_lossy(&buf);
    println!("{}", s);
---------------------------------------------------------------------------------------------------------------------------*/

use std::io::{Read};
use std::fs::{File};

fn main() {
    let mut f: File = File::open("test.txt").unwrap_or_else(|err| {
        eprintln!("ERROR: {}", err);
        std::process::exit(1);
    });

    let mut buf = [0u8; 10];
    let size: usize;

    size = f.read(&mut buf).expect("cannot read file!..");
    println!("{} bytes read: {:?}", size, buf);
    let s = String::from_utf8_lossy(&buf);
    println!("{}", s);
}

/*---------------------------------------------------------------------------------------------------------------------------
    Biz yukarıda Read trait'indeki zorunlu metodu inceledik. Yukarıda da belirttiğimiz gibi Read trait'inde bu zorunlu metot 
    kullanılarak gerçekleştirilmiş olan metotlar da hazır bulunmaktadır. Trait'in read_to_end metodu gerekiyorsa birden fazla 
    read çağrısı yaparak dosya göstericisinin gösterdiği yerden itibaren dosya sonuna kadar tüm byte'ları dosyadan okuyarak 
    parametresiyle aldığı vektöre yerleştirmektedir. Metodun parametrik yapısı şöyledir:

    buf parametresi Vec<u8> türünden bir vektörün referansını almaktadır. Metot vektöre yerleştirdiği byte sayısıyla ya da 
    hata değeri ile geri dönmektedir. Örneğin:

     let mut f: File = File::open("test.txt").unwrap_or_else(|err| {
        eprintln!("ERROR: {}", err);
        std::process::exit(1);
    });

    println!("{}", s);

    fn read_to_string(&mut self, buf: &mut String) -> Result<usize>

    });
    println!("{}", s);

    eylemi Seek isimli trait ile soyutlanmıştır. Seek trait'inin elemanları şunlardır:

    pub trait Seek {
        // Required method
        fn seek(&mut self, pos: SeekFrom) -> Result<u64>;

        // Provided methods
        fn rewind(&mut self) -> Result<()> { ... }
        fn stream_len(&mut self) -> Result<u64> { ... }
        fn stream_position(&mut self) -> Result<u64> { ... }
        fn seek_relative(&mut self, offset: i64) -> Result<()> { ... }
    }

    fn seek(&mut self, pos: SeekFrom) -> Result<u64>;

    pub enum SeekFrom {
        Start(u64),
        End(i64),
        Current(i64),
    }

    örneğin SeekFrom::Start(1000) gibi oluştururuz. Tabii bidiğiniz gibi hedef tür zaten belliyse (seek metounda bellidir)
    bu durumda Rust'ta enum varyantları için enum isminin kullanılmasına gerek yoktur. Metot başarı durumunda konumlandırılan 
    offset değerine, başarısızlık durumunda hata değerine geri dönmektedir. Start, End ve Current varyantları diğer programlama

/*---------------------------------------------------------------------------------------------------------------------------
    Şimdi de tamponlu okuma yazma işlemleri üzerinde duralım. File yapısı okuma yazma işlemini bir tampon kullnmadam doğrudan 
    yapmaktadır. Örneğin biz Rust'ta bir döngü içerisinde File yapısının read metodu ile okumalar yaptığımızda bu metot her 
    defasında arka planda işletim sisteminin düşük seviyeli read/write fonksiyonlarını çağırıp tekrar tekrar transfer yapmaktadır. 
    Bir dosyadaki karakterleri tek tek sırasıyla okuyup parse etmek isteyelim. Her karakteri okurken yeniden read/write 
    işleminin yapılması oldukça verimsizdir. İşte programlama dillerinin standart kütüphaneleri bu read/write çağrılarını
    azaltmak için tamponlama (buffering) uygulamaktadır. C'nin stdio fonksiyonları, C++'ın iostream fonksiyonları Java ve 
    C#'taki dosya sınıfları hep tamponlu bir biçimde çalışmaktadır. Tamponlu çalışmada okuma sırasında talep edilenden 
    daha fazla okuma yapılarak tampon doldurulur. Sonraki okumalarda read işlemi yapmak yerine doğrudan bu tampondan 
    istek karşılanır. Tamponun dışına çılıkdığında yeniden read işlemi yapılır. Yazma durumu da benzerdir. Yazma da doğrudan
    tampona yapılmaktadır. Ancak tampon dolduğunda write fonksiyonları ile aygıta aktarım yapılmaltadır. Tabii bazen 
    programcı tampondaklerin o anda disteki dosyaya yazılmasını isteyebilir. Bu işleme "flush" işlemi denilmektedir. 

    Rust'ta File yapısının herhangibir tanpon kullanmadığını belirtmiştik. İşte Rust'ta tamponlu okuma ve yazmalar için 
    BufReader ve BufWriter isimli yapılar kullanılmaktadır. 
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    Rust'ta BufReader ve BufWriter yapıları yalnızca File yapısı için tasarlanmamaıştır. Bu trait'ler aslında Reda ve Write 
    trait'lerini destekleyen herhangi bir tür için tamponlama yapanilmektedir. Biz önce BufReader yapısını sonra BufWriter 
    yapısını ele alacağız. 

    BufReader yapısı şöyle tanımlanmıştır:

    pub struct BufReader<R: ?Sized> { /* private fields */ }

    BufReader yapısının imp bloğu şöyle oluşturulmutur:

    impl<R: Read> BufReader<R> {
        //...
    }

    Görüldüğü gibi BufReader yapısının generic parametresi Read trait'ini destekleyen bir tür türündne olmak zorundadır. 
    File yapısı Read trait'ini desteklediğine göre geberic parametre kullanılabilir. 
    
    Bir BufReader nesnesi yapının ilişkili new fonksiyonuyla yaratılmaktadır. new fonksiyonunun parametrik yapısı şöyledir:

    pub fn new(inner: R) -> BufReader<R>

    Görüldüğü gibi new fonksiyony Read trait'ini destekleyen bir değeri parametre olarak alıp BufReader değeri ile
    geri dönmektedir. Örneğin:

    let mut f: File = File::open("test.txt").unwrap_or_else(|err| {
        eprintln!("ERROR: {}", err);
        std::process::exit(1);
    });
    let mut buf_reader = BufReader::new(f);
    
    BufReader yapısı BufRead isimli trait'i desteklemektedir. BufRead trait'i tamponlama işlemleri için arayüz oluşturmaktadır:

    pub trait BufRead: Read {
        // Required methods
        fn fill_buf(&mut self) -> Result<&[u8]>;
        fn consume(&mut self, amount: usize);

        // Provided methods
        fn has_data_left(&mut self) -> Result<bool> { ... }
        fn read_until(&mut self, byte: u8, buf: &mut Vec<u8>) -> Result<usize> { ... }
        fn skip_until(&mut self, byte: u8) -> Result<usize> { ... }
        fn read_line(&mut self, buf: &mut String) -> Result<usize> { ... }
        fn split(self, byte: u8) -> Split<Self> ⓘ
        where Self: Sized { ... }
        fn lines(self) -> Lines<Self> ⓘ
        where Self: Sized { ... }
    }

    Trait'in Read trait'inden türetildiğine dikkat ediniz. Yani bu destelyecek tür Read trait'ini de desteklemek 
    zorundadır. Görüldüğü gibi BufRead trait'inin iki zorunlu metodu vardır: fill_buf ve consume. fill_buf metodu  
    read metodunu çağırarak doldurur ve başarı durumunda içsel tampona ilişkin dilim referansıyla geri döner. Bu metodun 
    çağrıldığında tamponu ne kadar dolduracağı konsunda bir belirleme yapılmamıştır. EOF durumuna gelindiyse metot boş 
    bir dilime ilişkin referansla geri dönmektedir. consume metodu içsel tampondaki belli miktarda byte okunmuş gibi 
    işaretleme yapmaktadır. 
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------

    Trait'in isteğe bağlı (provided) metotları zorunlu metotlar kullanılarak yazılmıştır. read_line metodu dosyadan bir
    satırlık bilgiyi okumak için kullanılmaktadır. Metoun parametrik yapısı şöyledir:

    fn read_line(&mut self, buf: &mut String) -> Result<usize>

    Metot okuduğu byte'ları String nesnesine yerleştirir, okuduğu byte sayısıyla geri döner. read_line metodu satır sonundaki 
    '\n' karakterini de okur ve onu da String içerisinde yerleştirir. Satır okuması yapam metotların tampon kullanması 
    gerektiğine dikkat ediniz. (Eğer satır okuyan metotlar tampon kullanmasaydı mecburen '\n' karakterini görene kadar 
    dosyadan byte'ları döngü içerisinde okumak zorunda kalırdı. Bu da çok yavaş olurdu.) Metot dosyanın sonuna gelindeiğinde 
    başarısız olmaz ancak 0 değeri ile geri döner. Örneğin:

    use std::fs::{File};
    use std::io::{BufReader, BufRead};

    fn main() {
        let mut f: File = File::open("test.txt").unwrap_or_else(|err| {
            eprintln!("ERROR: {}", err);
            std::process::exit(1);
        });

        let mut buf_reader = BufReader::new(f);
        let mut s = String::new();
        let mut n: usize;

        loop {
            n = buf_reader.read_line(&mut s).unwrap_or_else(|err| {
                eprintln!("ERROR: {}", err);
                std::process::exit(1);
            });
            if n == 0 {
                break;
            }
    ;       print!("{}", s);
            s.clear();
        }
    }

    Burada döngü içerisinde read_line metodu ile satırlar okunmuştur. read_line metodunun başrı durumunda geri dönüş değeri 
    kontrol edilmiş ve eğer dosyadan 0 byte okunmuşsa artık döngüden çıkışmıştır. read_line metodu okunanları String'in 
    sonuna push etmektedir. Bu nednele biz her okumadna sonra String değişkenini clear ettik. 
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    BufRead trait'inin read_until metodu belli bir byte'ı görene kadar (o byte dahil olmak üzere) tamponlu okuma yapmaktadır. 
    Okunanlar Vec<u8> içerisine yerleştirilmektedir. Metodun paramtrik yapısı şöyledir:

    fn read_until(&mut self, byte: u8, buf: &mut Vec<u8>) -> Result<usize>

    Metot yine başarı durumunda yerleştirilen byte sayısı ile geri dönmektedir. EOF durumu başarısızlık anlamına gelmez. Bu 
    durumda yine metot 0 değeriyle geri döner. Örneğin:

    n = buf_reader.read_until(0x61u8, &mut v).unwrap_or_else(|err| {
        eprintln!("ERROR: {}", err);
        std::process::exit(1);
    });

    0x61 numaralı karakter 'a' karakteridir. read_until bu karakteri görene kadar okuma yapmaktadır. 

    use std::fs::{File};
    use std::io::{BufReader, BufRead};

    fn main() {
        let mut f: File = File::open("test.txt").unwrap_or_else(|err| {
            eprintln!("ERROR: {}", err);

    girişinin ismini DirEntry yapısının file_name metodu ile elde ettik. Bu metotun parametrik yapısına dikkat ediniz:

    pub fn file_name(&self) -> OsString

    türünden bir değeri String türüne dönüştürmek için into_string metodu kullanılmaktadır. Metodun parametrik yapısı şöyledir:

    pub fn into_string(self) -> Result<String, OsString>;

    OsString içerisindeki yazı UTF-8 formatıyla ifade ediilemiyorsa metot başarısız olmakydır. 

    Örneğin:

    let mut os = OsString::new();

    os.push("a.dat");

    let s = os.into_string().expect("cannot convert String");
    println!("{}", s);

    to_string_lossy metodu Deref<Target=OsString> trait'inden galmektedir. Bu metot eğer OsString içerisindeki yazı 
    UTF-8 formatında geçerli değilse dönüştürmeyi yapar ancak geçersin karakterlere ? yerleştirir. Örneğin:

    let mut os = OsString::new();
    os.push("a.dat");

    let s = os.to_string_lossy();
    println!("{}", s);

    Elimizde OsString türünden bir değer varsa biz doğrudan to_str metodu ile onu string dilim referansına dönüştürebiliriz. 
    Metodun paramtrik yapısı şöyledir:

    pub fn to_str(&self) -> Option<&str>

    Örneğin:

    let mut os = OsString::new();
    os.push("a.dat");

    let s: &str = os.to_str().expect("imvalid conversion!..");
    println!("{}", s);

    OsStr türü OsString türünün statik biçimi için düşünülmüştür. Başka bir deyişle String ile str arasındaki ilişki 
    OSString ile OsStr arasındaki ilişki gibidir. OsStr türünden bir değer yaratılamaz. Ancak bir referans oluşturulabilir. 
    Örneğin:

    let os_str: &OsStr = OsStr::new("foo");

    Burada os_str değişkeni aslında bir adres ve bir uzunluk tutmaktadır. Elimizde bir OsStr varsa OsSting yapısının from 
    ilişkili fonksiyonu ile onu OsString türüne dönüştürebiliriz. Örneğin:

    let os_str = OsStr::new("foo");
    let os = OsString::from(os_str);

    Benzer biçimde elimizde OsStr türünden bir değer varsa to_os_string metodu ile onu OsString türüne dönüştürebiliriz:

    let os_str = OsStr::new("foo");
    let os: OsString = os_str.to_os_string();

    pub fn open<P: AsRef<Path>>(path: P) -> Result<File>

    Bu fonksiyon generic bir fonksiyondur. Generic parametresi AsRef<Path> trait'ini desteklemek zorundadır. Anımsanacağı 
    gibi AsRef<T> trait'i şöyle tanımlanmıştır:

    pub trait AsRef<T>
    where
        T: ?Sized,
    {
        // Required method
        fn as_ref(&self) -> &T;
    }

    Görüldüğü gibi trait'in as_ref isminde zorunlu bir metodu vardır. Bu metot çağrıldığında T türündne bir referans vermektedir. 
    open ilişki fonksiyonun tür sınırlamasına dikkat ediniz:

    <P: AsRef<Path>

    O halde bir türün yol ifadesi olarka kullanılabilmesi için AsRef<Path> trait'ini destekliyor olması gerekir. Başka bir 
    deyişle o tür içerisinde aşağıdaki gibi bir metodun bulunuyor olması gerekir:

    fn as_ref(&self) -> &Path

    ┌────────────────┬──────────────────────────────────────────────┐
    │      Tür       │                   Açıklama                   │
    ├────────────────┼──────────────────────────────────────────────┤
    │ Path           │ Kimlik impl'i; &Path -> &Path                │
    │ PathBuf        │ Sahipli (owned) path türü                    │
    │ &OsStr         │ Platforma özgü string dilimi                 │

    │ &str           │ UTF-8 dilim; "a/b" literalleri buradan gelir │
    │ String         │ Sahipli UTF-8 string                         │
    │ Cow<'_, OsStr> │ Ödünç ya da sahipli OsStr                    │

    │ Components<'_> │ Henüz tüketilmemiş kalan path'i verir        │
    │ Iter<'_>       │ path::Iter; kalan path'i verir               │
    └────────────────┴──────────────────────────────────────────────┘

    Burada bizim için en önemli olan türler şunlardır: &str, String, &OsStr, OsString, Path ve PathBuf.

/*---------------------------------------------------------------------------------------------------------------------------
    Rust'ta birlikler tıpkı C'de olduğu gibi alanların çakışık yerleştirildiği veri yapılarıdır. Biz enum türünün de elemanlarının
    çakışık yerleştirildiğini görmüştük. Doğal olarak "mademki enum türü de birlik gibi çakışık yerleştiriliyor, o zaman 
    birliklere ne gerek var?" sorusu aklınıza gelebilir. Rust'ın enum türü kalıp uyuşumu ile çalışan daha karmaşık bir türdür. 
    enum türünde kalıp uyuşumu için enum varyantının hangisinin set edildiğini belirten bir "ayırıcı değerin de (discriminant)"
    değişken içerisinde yer kapladığını anımsayınız. Rust'ın birlikleri C'nin birliklerine benzemektedir. Dolayısıyla bir 
    birlik türünden değerde bir ayırıcı değer bulundurulmaz. Rust'ın birlikleri özellikle C ile etkileşim amacıyla bulundurulmuştur. 
    Aşağıdaki tabloda Rust'taki enum türüyle union türü arasındaki farklılıklar belirtilmektedir:

    ┌────────────────┬──────────────────────────┬─────────────────────────────┐
    │                │     Etiketli birlik      │       Etiketsiz birlik      │
    │                │      (tagged union)      │       (untagged union)      │
    ├────────────────┼──────────────────────────┼─────────────────────────────┤
    │ Rust karşılığı │ enum                     │ union                       │
    ├────────────────┼──────────────────────────┼─────────────────────────────┤
    │ Aktif varyantı │ Evet — gizli bir ayırıcı │ Hayır — aktif alan bilgisi  │
    │ saklar mı?     │ (discriminant) tutar     │ tutulmaz                    │
    ├────────────────┼──────────────────────────┼─────────────────────────────┤
    │ Güvenlik       │ Tamamen güvenli; match   │ Alan okuma unsafe;          │
    │                │ derleyici tarafından     │ geçerlilik programcıda      │
    │                │ denetlenir               │                             │
    ├────────────────┼──────────────────────────┼─────────────────────────────┤
    │ Boyut          │ En büyük varyant +       │ En büyük alan (+ hizalama); │
    │                │ ayırıcı (+ hizalama)     │ ayırıcı değer yok           │
    ├────────────────┼──────────────────────────┼─────────────────────────────┤
    │ Ana kullanım   │ Sıradan Rust modellemesi │ FFI, düşük seviye, tip      │
    │                │                          │ yeniden yorumlama           │
    └────────────────┴──────────────────────────┴─────────────────────────────┘

    Bir birlik union anahtar sözcüğüyle tanımlanır. Alan bildirimleri yapılarla aynıdır. Örneğin:

    union U {
        a: i32,
        b: i64,
        c: [u8; 12]
    }

    Burada birliğin üç alanı vardır. Bu alanlar tıpkı C'de olduğu gibi çakışık yerleştirilmektedir. Bir birlik türünden 
    değer için C'de olduğu gibi birliği en büyük elemanı kadar yer ayrılmaktadır. Örneğin:

    fn main() {
        println!("{}", std::mem::size_of::<U>());       // 16
    }

    union U {
        a: i32,
        b: i64,
        c: [u8; 12]
    }

    Birliğin alanları herhangi bir türden olamaz. Birlik alanları Copy türünden olmak zorundadır. Ancak Copy türünden 
    dizi ve demet de içerebilir. Birlik alanları gösterici ve referans da olabilir. Örneğin:

    union U {
        a: i32,
        b: i64,
        c: Sample       // error!
    }

    struct Sample {
        name: &'static str,
        no: i32
    }

    Ancak örneğin:

    union U {
        a: i32,
        b: i64,
        c: Sample       // geçerli
    }

    #[derive(Copy, Clone)]
    struct Sample {
        name: &'static str,
        no: i32
    }

    union U<'a> {
        a: i32,
        b: i64,
        c: &'a Sample
    }

    struct Sample {
        name: &'static str,
        no: i32
    }

        a: i32,
        b: f64,
        c: [i32; 3]

    ├── rust_2018   // re-exports v1

    ├── rust_2024   // rust_2021 + Future, IntoFuture
    └── rust_future // unstable: the prelude of the *next* edition (nightly only)

/*---------------------------------------------------------------------------------------------------------------------------
    Biz yukarıda standard prelude sayesinde hiç use işlemi yapmadan doğrudan kullanabileceğimiz isimleri listeledik. Rust'ta 
    standard prelude'e programcı yeni bir öğe ekleyememektedir. Eğer programcı yukarıdaki standard prelude içerisinde olmayan 
    pek çok farklı ismi kullanmak isterse en pratikj yöntem bir crate oluşturup onun kökünde use bildirimlerini yapıp, 
    modülü "Cargo.toml" dosyasında belirtip onu use etmektir. Örneğin:

    use myprelude::*;

    Bu örnekten de anlaşılacağı gibi içeirisnd pub use bildirimleri olan crate'ler derlenip başka bir modülden use edilebilmektedir. 
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    Standard prelude'teki isimler ezilebilir mi? Bunlara isim araması sırasında hangi aşamada başvurulmaktadır? İşte her ne 
    kadar biz standart prelude'ün içerisindeki use deyimlerinin sank modülün başına yerleştirilmiş gibi etki gösterdiğini 
    belirtsek de aslında isim araması bakımından bazı farklılıklar da söz konusudur:

    - Modülde tanımlı bir öğe (item) prelude'teki isimleri gölgeler.
    - Açık bir use bildirimi prelude içerisindeki isimleri gölgeler.
    - Bir glob import (yabi use m::* işlemş) prelude içerisindeki isimleri gölgeler. 
    
    Standard prelude bağlamında isim araması da şöyle yapılmaktadır (else-if biçiminde):

    1) İsim önce yerel bloklarda aranır.
    2) İsim kullanılan modülde aranır. 
    3) İsim glob import'larda (yani use m::* gibi) aranır.
    4) İsim standart Standart prelude içerisinde aranır. 
    
    use bildiriminin ismi ilgili faaliyet alanına soktuğunu anımsayınız. Bu sıra üzerinde bazı örnekler verelim. 
    Örneğin:

    fn main() {
        let v = Vec{};      // Bizim tanımladığımız Vec

        v.disp();           // geçerli
    }

    struct Vec {
        //...
    }

    impl Vec {
        fn disp(&self) {
            println!("My Vec");
        }
    }

    Vec ismi standart prelude içerisinde bulunmaktadır. Ancak yukarıdaki isim arama sırasına bakıldığında isim önce main 
    fonksiyonun yerel bloğunda, sonra modülün kökünde aranacaktır. Standard prelude arama sırasının sonundadır. Bu nedenle 
    buradal Vec bizim tanımladığımız Vec yapısıdır. Örneğin:

    fn main() {
        //...
    }

    mod module_a {
        pub struct Vec {
            //...
        }

        impl Vec {
            fn disp(&self) {
                println!("My Vec");
            }
        }

        mod module_b {
            fn foo() {
                let v = Vec {};      // error! prelude içerisindeki standart Vec

                v.disp();           // error!
            }
        }
    }

    Burada C++, C# gibi dillerden geçenler modeule_b içerisindeki foo fonksiyonunda kullanılan Vec isminin üst modüldeki
    Vec olması gerektiğini düşünebilmektedir. Oysa anımsnacağı gibi Rıst'ta isim araması ırasında üst modüle hiç bakılmamaktadır. 
    Dolayısıyla buradaki Vec artık bizim tanımladığımız Vec değil standrat prelude içerisinde bulunan standart kütüphanedeki 
    Vec yapısıdır. 

    Örneğin:
    
    fn main() {
        //...
    }

    pub struct Vec {
        //...
    }

    impl Vec {
        fn disp(&self) {
            println!("My Vec");
        }
    }

    mod a_module {
        mod b_module {
            use crate::Vec; 

            fn foo() {
                let v = Vec {};      // geçerli, bizim tanımladığımız Vec
                v.disp();           // geçerli
            }
        }
    }
    
    use bildiriminin faaliyet alanına değişken soktuğuna dikkat ediniz. Bu nedenle artık Vec ismi b_module içerisinde 
    bildirilmiş bir isim gibidir. Dolayısıyla isim araması sırasında bulunacaktır. 

    use bildiriminin glob biçiminde ilgili modüldeki isimlerin hepsi faaaliyet alanına sokulmaktadır. Ancak isim arama 
    sırasına dikkat edildiğinde ismin kullanıldığı modüle önce bakılmaktadır. Örneğin:

    fn main() {
        //...
    }

    mod a_module {
        struct Sample(i32);

        mod b_module {
            use super::*;

            struct Sample(i32, i32);

            fn foo() {
                let s = Sample(10, 20);     // geçerli, glob daha düşük öncelikli
                //...
            }
        }
    }
    
    Burada hem module_a içerisinde hem de module_b içerisinde Sample isimli iki tanımlanmıştır. Buradaki glob use işlemi 
    bir isim çakışmasına yol açmayacaktır. Çünkü yukarıdaki sıraya göre Sample ismi modülde bulunduğu için glob ile 
    sokulan Sample dikkate alınmayacaktır.
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    Anımsanacağı gibi C'de ve C++'ta main fonksiyonun geri dönüş değeri int olmak zorundadır. Ancak o dillerin standartları 
    main fonksiyonun geri dönüş değerinin eğer derleyici izin veriyorsa (implementaion dependent) başka bir tür de olabileceğini 
    belirtmektedir. Peki Rust'ta durum nasıldır?

    Rust'ta main fonksiyonun parametresi yoktur. Ancak geri dönüş değeri std::process::Termination isimli bir trait'i 
    destekleyen bir türdne olmak zorundadır. Termination trait'i şöyle tanımlanmıştır:

    pub trait Termination {
       // Required method
        fn report(self) -> ExitCode;
    }

    Görüldüğü gibi bu trait'i destekleyen türün report isimli bir metodu olmak zorundadır. Bu metot da ExitCode türünden 
    bir değerler geri dönmektedir. ExitCode std::proscess modülünde bir yapı biçiminde tanımlanmıştır. Bu yapının içerisinde 
    ExitCode türünden iki const değişken vardır: FAILURE ve SUCCESS. Yani bir ExitCode değeri örneğin ExitCode::FAILURE 
    ya da ExitCode::SUCCESS biçiminde oluşturulabilir. 
    
    ExitCode yapısı From<u8> trait'in de desteklemektedir. Yani yapıda u8 türünden parametreye sahip bir from metodu da 
    vardır. Bu duurmda biz ExitCode yapısı türünden değeri ExitCode::from(değer) biçiminde de oluşturabiliriz. ExitCode 
    yapısının ifade ettiği çıkış kodunun u8 türünden (yani 0 ile 255 arasında) olmak zorunda olduğuna dikkar ediniz. 
    
    ExitCode yapısının aşağıdaki biçimde tanımlanmış olduğunu varsyabilirsiniz:

    struct ExitCode(u8);

    impl ExitCode {
        const FAILURE: ExitCode = ExitCode(1);
        const SUCCESS: ExitCode = ExitCode(0);
    }

    impl std::convert::From<u8> for ExitCode {
        fn from(value: u8) -> Self {
            ExitCode(value)
        }
    }
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    Şimdi biz main fonksiyonunu kendi yapımız türünden bir değerle geri döndürmek isteyelim. Yapımızın std::process::Terination 
    destekliyor olması gerekir. Örneğin:

    fn main() -> MyExitStruct {
        println!("main...");
        MyExitStruct
    }

    struct MyExitStruct;

    impl std::process::Termination for MyExitStruct {
        fn report(self) -> std::process::ExitCode {
            println!("my report method");
            std::process::ExitCode::SUCCESS
        }
    }

    main programı sonlanırken report metodu çağrılmaktadır. Dolayısıyla bu programı çalıştırdığımızda ekranda şunları 
    göreceğiz:

    main...
    my report method

    Tabii uygulamada programcılar nadiren main fonksiyonunu kendi türlerine ilişkin bir değerle geri döndürmektedir. Rust'ta
    aşağıdaki türler zaten Termination trait'ini desteklemektedir:

    ()
    !
    Infallible
    ExitCode
    Result<T, E> where T: Termination, E: Debug

    Örneğin birim türü Termination trait'ini desteklemektedir. Zaten biz şimdiye kadar main fonksiyonuna bir geri döüş 
    değeri türü yazmadık. main fonksiyonunu hep şöyle kullandık:

    fn main() {
        //...
    }

    Anımsanacağı gibi Rust'ta bir fonksiyonda -> atomu ile geri dönüş değerinin türü belirtilmezse fonksiyonun geri dönüş 
    değeri () türünden ("birim (unit)" türünden) kabul edilmektedir. Yani aşağıdaki iki tanımlama tamamen eşdeğerdir:

    fn main() {
        //...
    }

    fn main() -> () {
        //...
    }

    Maalesef Rust dokğmantasyonlarında birim türünün report metodunun hangi ExitCode değeriyle geri döndüğü açık bir 
    biçimde belirtilmemiştir. Muhtemelen bu durum dokümantasyonda bir hatadır. Ancak standart kütüphane dokümanlarında 
    birim türünün report metodunun aşağıdaki gibi yazıldığı görülmektedir:

    impl Termination for () {
        #[inline]
        fn report(self) -> ExitCode {
            ExitCode::SUCCESS
        }
    }

    ! türü (yani "never" türü) "geri dönmemeyi" belirttiğinden dolayı Termination trait'ini de şeklen desteklemektedir. 

    ExitCode yapısının kendisi de Termination trait'ini desteklemektedir. O halde örneğin biz main fonksiyonunu şöyle 
    geri döndürebiliriz:

    fn main() -> std::process::ExitCode {
        println!("main...");
        
        std::process::ExitCode::SUCCESS
    }

    Standart kütüphane kaynak kodlarında ExitCode yapısında report metodu şöyle yazılmıtır:

    impl Termination for ExitCode {
        #[inline]
        fn report(self) -> ExitCode {
            self
        }
    }

    Bu durumda örneğin biz yukarıdai main fonksiyonunu std::process::ExitCode::SUCCESS değeriyle geri döndürdüğümzde 
    main biterken bu değer ile report metodu metodu çağrılacak, report metodu da self ile geri döndüğü için std::process::ExitCode::SUCCESS
    değeri elde edilecektir. 

    Aşağıdaki generic parametre koşulunu sağlayan Result türü de Termination trait'ini desteklemektedir:

    Result<T, E> where T: Termination, E: Debug

    Görüldüğü gibi eğer Result enum türünün Ok varyantının türü Termination trait'ini destekliyorsa ve Err varyantının türü 
    de std::fmt::Debug trait'ini destekliyorsa Result türü main fonksiyonunun geri dönüş değeri türü olarak kullanılabilmektedir. 
    Türlerin çoğu zaten std::fmt::Debug trait'ini desteklemektedir. Bu türün report metodu da standart kütüphane kaynak 
    kodlarında şöyle yazılmıştır:

    impl<T: Termination, E: fmt::Debug> Termination for Result<T, E> {
        fn report(self) -> ExitCode {
            match self {
                Ok(val) => val.report(),
                Err(err) => {
                    io::attempt_print_to_stderr(format_args_nl!("Error: {err:?}"));
                    ExitCode::FAILURE
                }
            }
        }
    }

    Buradan şu sonuş çıkmaktadır: Eğer biz main fonksiyonunu Ok(ok_val) değeri ile geri döndürürsek geri döndürdüğümüz 
    ok_val değeri ile report metodu çağrılıp report metodunun geri dönüş değeriyşe main fonksiyonu geri döndürülmektedir. eğer 
    biz main fonksiyonunu Err(err_val) değeri ile geri döndürürsek bu durumda da err_val değeri debug mesajı olarak standarr
    error dosyasına yazdırılıp main fonksiyonu std::process::ExitCode::FAILURE değeir ile geri döndürülmektedir. Örneğin:

    fn main() -> Result<MyExitStruct, &'static str> {
        println!("main...");

        Ok(MyExitStruct)
    }

    struct MyExitStruct;

    impl std::process::Termination for MyExitStruct {
        fn report(self) -> std::process::ExitCode {
            println!("my report method");
            std::process::ExitCode::SUCCESS
        }
    }

    Burada biz main fonksiyonunu Ok(MyExitStruct) ile geri döndürdük. MyExitStruct türü Termination trait'i desteklediği 
    için aslında bu türün report metodu çağrılacaktır. main fonksiyonunu şöyle yazmış olalım:

    fn main() -> Result<MyExitStruct, &'static str> {
        println!("main...");

        Err("terimantion error!..")
    }

    Burada önce "termination error!.." mesajı standart error dosyasına debug mesajı olarak basılacak ve main fonksiyonu 
    std::process::ExitCode::FAILURE değeriyle geri dönecektir. 
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    Gördüğünüz gibi Rust'ta main fonksiyonunun geri dönüş değeri konusu biraz karışıktır. Tabii programcı bu karışıklığa 
    hiç girmeden main fonksiyonunu birim değeriyle geri döndürebilir. Ancak bu tasarım çok daha gelişmiş geri dönüş durumlarını 
    desteklemektedir. Aşağıda main fonksiyonun geri dönüş değeri olarak bir enum türünün kullanıldığı bir örnek görüyorsunuz
---------------------------------------------------------------------------------------------------------------------------*/

fn main() -> Outcome {
    Outcome::Warnings(4)
}

use std::process::{ExitCode, Termination};

enum Outcome {
    Clean,
    Warnings(u8),
    Fatal(String),
}

impl Termination for Outcome {
    fn report(self) -> ExitCode {
        match self {
            Outcome::Clean => ExitCode::SUCCESS,
            Outcome::Warnings(n) => {
                eprintln!("{n} warning(s)");
                ExitCode::from(2)
            }
            Outcome::Fatal(msg) => {
                eprintln!("fatal: {msg}");
                ExitCode::from(3)
            }
        }
    }
}

/*---------------------------------------------------------------------------------------------------------------------------
    İşletim sistemlerinde çalışmakta olan programlara "proses (process)" denilmektedir. Proses canlı bir varlıktır. İşletim 
    sistemi bir program çalıştırıldığında çekirdeği içerisinde çalışırılan program için pek çok veri yapısı oluşturmaktadır. 
    Proses yalnızca bir akış değildir. Çalışmakta olan programın bütün bilgilerini temsil etmektedir. 
    
    Thread'ler bir proseslerin ayrı bir biçimde çizelgelenen farklı akışlarıdır. Bir proses çalışmaya tek bir thread'le başlar. 
    Buna prosesin ana thread'i (main thread) denilmektedir. Diğer thread'ler daha sonra programcı tarafından yaratılmaktadır. 
    Thread'ler aynı program üzerinde ilerleyen farklı akışlardır. Thread'ler işletim sistemlerine 90'lı yıllarda sokulmuştur. 
    Thread kullanımının mümkün olduğu işletim sistemlerine "çok thread'li (multi-threaded)" işletim sistemleri denilmektedir. 
    Windows, Linux, macOS thread kullanımının mümkün olduğu "çok thread'li (multi-threaded)" işletim sistemleridir.                                   
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    Modern çok prosesli ve çok thread'li işletim sistemlerinde thread'ler "zaman paylaşımlı (time sharing)" bir biçimde 
    çalıştırılmaktadır. İşletim sistemi thread'leri bir kuyrukta tutar. Bu kuyruğua genellikle "çalışma kuyruğu (run queue)"
    denilmektedir. Sonra kuyruktan bir thread'i alır. Onu CPU'ya atar. O thread'in belli bir süre çalışmasını sağlar. Sonra 
    o süre dolduğunda thread'in çalışmasına ara verir. Sıraki thread'i CPU'ya atar ve çalışma "biraz onu biraz bundan" biçiminde 
    devam ettirilir. Kullanıcılar programların aynı anda çalıştığını sanırlar. Ancak aslında programlar bu biçimde kesikli 
    kesikli çalışmaktadır. Bir thread'in CPU'ya atanıp çalıştırıldığı parçalı zaman süresine "quantum süresi (time quantum)" 
    denilmektedir. Quantum süresini bitiren (ya da bloke olan) bir thread'in CPU'dan koparılarak sıradaki thread'in CPU'ya 
    atanması sürecine ise "bağlamsal geçiş (context switch)" ya da "görev geçişi (task switch)" denilmektedir. Quantum süreleri 
    işletim sistemi tarafından uygun biçimde belirlenmektedir. 

    Birden fazla CPU'nun ya da çekirdeğin bulunduğu durumda zaman paylaşımlı çalışma benzer biçimde yürütülmektedir. Genellikle 
    işletim sistemleri her CPU ya da çekirdek için ayrı bir çalışma kuyruğu oluştururlar. Böylece toplamda birim zamanda yapılan 
    iş miktarı da artırılmış olur. Bu durumu süpermarketlerdeki birden fazla kasanın bulunmasına benzetebiliriz. Bazı işletim 
    sistemleri tek bir çalışma kuyruğu oluşturup bir CPU ya da çekirdekte thread'ler arası geçiş olacağı zaman o tek kuyruktan 
    çizelgeleme yapmaktadır. Bu tarzda kuyruklar yine gündelik hayatta karşımıza çıkabilmektedir. Yani çok CPU ya da çekirdek 
    olması zaman paylaşımlı çalışmayı ortadan kaldırmamaktadır. 

    İşletim sistemlerinde thread'leri CPU kuyruklarına yerleştirilmesi, CPU'ya atanması, bağlamsal geçiş (context switch) 
    işlemlerini yapan alt sisteme "çizelgeleyici (scheduler)" denilmektedir.                                          
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    Peki thread'lere neden gereksinim duyulmaktadır? Bunları birkaç madde halinde özetleyebiliriz:

    1) Thread'ler arka plan periyodik işlemlerin yapılabilmesi için iyi bir araç oluşturmaktadır. Örneğin bir program çalışırken 
    aynı zamanda saati ekranın bir yerine basacak olsun. Tek bir akışla bu işlemi yapmak çok zordur. Çünkü ana akış input gibi 
    bir fonksiyona girdiğinde artık saati basma imkanı kalmaz. Ana akışın input gibi bir fonksiyona girmese bile hem bir işi 
    yaparken periyodik başka bir işlemi yapması çok zordur. Halbuki çok thread'li programlamada bir thread yaratılır ve arka 
    plan periyodik işlemler bu thread'e havale edilir. Böylece programın ana akışı ilerlemeye devam eder. Ondan bağımsız bir 
    biçimde yaratılan thread periyodik işlemleri yapar. Thread'ler biribinden bağımız olarak sanki ayrı programlarmış gibi 
    çalışmaktadır. Bir thread'in bir noktada beklemesi (teknik olarak "bloke olması") diğer thread'lerin çalışmasını engellememektedir.

    2) Thread'ler bir işi hızlandırmak için de kullanılmaktadır. Bir işi tek bir akışa yaptırmak yerine biren fazla akışa 
    yaptırabilirsek o işin daha hızlı bitirilmesini saplayabiliriz. 

    3) Thread'ler "paralel programlama (parallel programming)" ortamı oluşturmak için de kullanılmaktadır. 

    4) GUI programlama modelinde bir mesaj oluştuğunda bir işlem yapmak istediğimizde o işlemi uzatmamalıyız. Aksi takdirde
    mesaj döngüsü işletilmemiş olur ve program donmuş gibi bir etki oluşur. Bu tür durumlarda bir mesaj oluştuğunda uzun 
    süren bir işlem yapılacaksa bir thread yaratılır, uzun sürecek işlem thread'e havale edilir. Eğer işlem iptal edilecekse 
    o thread öldürülür. Yani GUI programlama modelinde therad'ler bazen mecburen kullanılmaktadır. 
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    Şimdi de Rust'ta temel thread işlemleri üzerinde duralım. Rust'ta thread işlemleri için std::thread modülündeki fonksiyonlar 
    ve yapılar kullanılnaktadır. Genellikle Rust programcıları bu modülü programın başında use ederler:

    use std::thread;

    Yeni bir thread yaratmak için spawn fonksiyonu kullanılmaktadır. Fonksiyonun parametrik yapısı şöyledir:

    pub fn spawn<F, T>(f: F) -> JoinHandle<T>
    where
        F: FnOnce() -> T + Send + 'static,
        T: Send + 'static,

    Bu parametrik yapı biraz karmaşık görünümdedir. Ancak burada ilk göze çarpan şey spawn fonksiyonunun generib bir 
    fonksiyon olmasıdır. Fonksiyonun iki generic parametresi vardır. Bu generi parametreler zaten girilen argümandan 
    otomatik çıkarsanmaktadır. spawn fonksiyonu "çağrılabilen (callable)" bir değeri parametre olarak alır. spwan 
    fonksiyonuna geri dönüş değeri T türünden olan (T burada generic herhangi bir türü temsil ediyor) parametresi olmayan 
    bir fonksiyon, kapanım (clusure) ya da çağrılabilen bir yapı türünden değişken olabilir. Söz konusu çağrılabilen nesne 
    ancak 'static ömre sahip olan dış bloklardaki değerleri kullanabilmektedir Çağrılabilen nesnenin geri dönüş değeri 
    de thread'ler arası taşınabilirliği olan (yani Send trait'ini destekleyen) bir tür türünden olmalıdır. spawn fonksiyonu 
    JoinHandle<T> türünden bir değerle geri dönmektedir. JoinHandle std::thread modülündeki bir yapıdır. JoinHandle yapısı 
    da generic bir yapıdır. Geneirc parametresi çağrılabilen nesnenin geri dönüş değeri türündendir. Örneğin biz spawn 
    fonksiyonuna geri dönüş değeri i32 türünden olan bir fonksiyonu argüman olarak geçirirsek spawn fonksiyonu da JoinHandle<i32> 
    türüyle geri dönmektedir. Örneğin biz spawn fonksiyonuna geri dönüş değeri birim olan (yani () türündne olan) bir 
    fonksiyonu parametre olarak geçirirsek spawn fonksiyonu bu durumda JoinHandle<()> türüyle geri dönecektir. Örneğin:

    let jh = thread::spawn(thread_proc);
    
    Burada örneğin thread_proc şöyle bir fonksiyon olabilir:

    fn thread_proc() {
        //...
    }

    spawn fonksiyonu yeni bir thread'in yaratılarak o thread'in belirtilen fonksiyonla (örneğimizdeki thread_proc) çalışmasını
    sağlamaktadır. Artık yukarıdaki işlemle birlikte programda iki thread söz konusu olmaktadır. Birincisi programın ana threadi, 
    ikincisi bizim spawn ile yarattıpımız thread. Programın ana thread'i yukarıda da belirttiğimiz gibi işletim sistemi tarafından 
    yaratılmaktadır. Ana thread'in başlangıç fonksiyonunun main olduğunu düşünebilirsiniz. Artuık yukarıdaki örnekte birbirinden 
    bağımısz olarak çizelgelenen (yani biri dursa da diğeri çalışmaya devam edebilecek olan) iki ayrı thread vardır. 

    Rust'ta tıpkı C'de olduğu gibi main fonksiyonu bittiğinde yalnızca ana thread değil tüm proses sonlanmaktadır. Thread'ler 
    proseslerin içerisinde akış belirtmektedir. Eğer akış main fonksiyonun ana bloğunu bitrirse programla birlikte tüm 
    thread'ler de sonlandırılmış olacaktır.
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    Aşağıdaki örnekte main fonksiyonu içerisinde bir thread yaratılmış sonra da hem ana thread hem de yaratılan thread 0'dan 
    5'e kadar sayıları 1 saniye bekleyerek ekrana (stdout dosyasına) yazdırmıştır:

    use std::thread;
    use std::time::Duration;

    fn main() {
        let jh = thread::spawn(thread_proc);

        for i in 0..5 {
            println!("main running: {}", i);
            thread::sleep(Duration::from_millis(1000));
        }
    }

    fn thread_proc() {
        for i in 0..5 {
            println!("thread running: {}", i);
            thread::sleep(Duration::from_millis(1000));
        }
    }

    Bu örnekte thread akışını belli süre bekletmek için thread modülündeki sleep fonksiyonu kullanılmıştır. sleep fonksiyonu
    time modülündeki Duration türünden bir değeri parametre olarak almaktadır. Duration değerini oluşturmanın çeşitli yolları 
    vardır. Duration yapısının from_millis ilişkili fonksiyonu belli bir milisaniyeye ilişkin Duration değeri oluşturmaktadır. 
    Yukarıdaki programı çalıştırdığımızda muhtemelen ekrana (stdout dosyasına) şunlar basılacaktır:

    main running: 0
    thread running: 0
    main running: 1
    thread running: 1
    main running: 2
    thread running: 2
    main running: 3
    thread running: 3
    main running: 4
    thread running: 4

    Yukarıda bşiz kasten "muhtemelen" sözcüğünü kullandık. Çünkü main fonks,yonu hizlı bir biçimde işlemini bitirirse 
    (bu durum çok da mümkün değildir) thread 4 değerini henüz ekrana (stdout dosyasına) basamayabilir. 

    Aşağıdaki programda maim akışı hemen biteceği için yaratılan thread de sonlandırılacaktır:

    use std::thread;
    use std::time::Duration;

    fn main() {
        let jh = thread::spawn(thread_proc);

        // dikkat! main akışı bitiyor, proses sonlanacak
    }

    fn thread_proc() {
        for i in 0..5 {
            println!("thread running: {}", i);
            thread::sleep(Duration::from_millis(1000));
        }
    }

    Peki ana thread'in main fonksiyonunu bitirmesini nasıl engelleyebiliriz? İlk akla gelen ana thread'i main fonksiyonunda 
    bekletmektir. Örneğin:

    use std::thread;
    use std::time::Duration;

    fn main() {
        let jh = thread::spawn(thread_proc);

        std::io::stdin().read_line(&mut String::new()).unwrap();
    }

    fn thread_proc() {
        for i in 0..5 {
            println!("thread running: {}", i);
            thread::sleep(Duration::from_millis(1000));
        }
    }

    Burada artık ana thread'te ENTER tuşuna basılana kadar akış bekletilmiştir. 

    İşte aslında yaratılmış olan bir thread'in sonlanmasının beklenmesi JoinHandle yapısının join isimli metoduyla yapılmaktadır. 
    join metodu ilgili thread sonlanana kadar kendisini thread akışını bloke ederek bekletir. join metodunun parametrik yapısı 
    şöyledir:

    pub fn join(self) -> Result<T>

    Görüldüğü gibi metot Result<T> türüne geri dönmektedir. Buradaki Result türü std::Result değildir. Buradaki Result 
    türü thread modülünde tanımlanmış olan Result türüdür:

    pub type Result<T> = Result<T, Box<dyn Any + Send + 'static>>;

    Buradan anlamamız gereken şey şudur: join metodu başarı durumunda Ok(T) değerine geri dönmektedir. Başarısızlık 
    durumunda ise Box<dyn Any + Send + 'static> türüne geri dönmektedir. join metodu UNIX/Linux sistemlerinde sinyal 
    dolayısıyla başarısız olabilir. Metot başarı durumunda thread fonksiyonunun (callable nesnesyi kastediyoruz) geri dönüş 
    değerini vermektedir. Örneğin:

    use std::thread;

    fn main() {
        let jh = thread::spawn(thread_proc);
        let result = jh.join().unwrap();

        println!("Result: {}", result);
    }

    fn thread_proc() -> i32 {
        let mut total = 0;

        for i in 1..=100 {
            total += i;
        }
        total
    }

    Burada thread fonksiyonun geri dönüş değeri i32 türündendir. join metodu da başarı durumunda Ok(i32) ile geri 
    dönmektedir. 

    Thread için işletim sistemleri çekirdek alanı içerisinde bazı nesneler oluşturmaktadır. Bu nesnelerin bazıları thread 
    join edilene kadar çekirdekte tahsis edilmiş bir biçimde tutulabilmektedir. Dolayısıyla eğer thread join edilemzse 
    işletim sistemi "her an join işlem yapılabilir diye bazı veri yapılarını çekirdek alanından boşaltmamaktadır. Bu duruma 
    UNIX türevi sistemlerde "zombie thread" durumu da danilmektedir. İşte thread'in join edilmesi aynı zamanda işletim 
    sisteminin tuttuğu kaynakların boşaltılmasını da sağlamaktadır. 

    Çok sayıda kısa ömürlü thread'lerin yaratıldığı uygulamalar seyrek değildir. Bu tür uygulamalarda her yaratılan thread'in
    join ile beklenmesi çoğu kez mümkün olmaz. İşte bu tür durumalrda thread'ler "detached" duruma sokulmalıdır. Bir thread 
    "detached" duruma sokulduğu zaman programcı işletim sistemine adeta şunları söylemektedir: "İşletim sistemi ben bu thread'in
    çıkıl kodunu (yani thrad fonksiyonunun geri dönüş değerini) almayacağım. Bu nedenle thread sonlandığında sen onun kaynaklarını 
    hemen boşalt". Rust'te thread'in detached duruma sokulması için JoinHandle değerinin drop edilmesi gerekmektedir. Drop
    işlemi sırasında drop fonksiyonu thread'i ilgili alt seviye fonksiyonu çağırarak detached duruma sokmaktadır. Örneğin:

    use std::thread;
    use std::time::Duration;

    fn main() {
        for _ in 0..100 {
            let jh = thread::spawn(thread_proc);
            drop(jh);
        }
        std::io::stdin().read_line(&mut String::new()).unwrap();
    }

    fn thread_proc() {
        for i in 0..10 {
            println!("{}", i);
            thread::sleep(Duration::from_millis(1000));
        }
    }

    Burada her yaratılan thread hemen "detached" duruma sokulmuştur. Dolayısıyla join gereksinimi de ortadan kaldırılmıştır. 
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    Birden fazla thread aynı fonksiyon üzerinde ilerleyebilir. Bu durumda fonksiyonun yerel değişkenleri bozulmaz. Çünkü 
    thread'lerin stack'leri birbirinden ayrılmıştır. Yerel değişkenlerin stack'te yaratıldığını anımsayınız. Her thread 
    akışı yerel değişkenlerin kendine özgü kopyasını kendi stack'inde oluşturmaktadır. Böylece iki thread akışı aynı 
    fonksiyon üzerinde ilerlerken aslında bu iki threda yerel değişkenlerin farklı kopyalarını kullanıyor durumda olur. 
    Örneğin:

    use std::thread;
    use std::time::Duration;

    fn main() {
        let jh1;
        let jh2;


        jh1 = thread::spawn(thread_proc);
        jh2 = thread::spawn(thread_proc);

        jh1.join().unwrap();
        jh2.join().unwrap();
    }

    fn thread_proc() {
        let mut total = 0;

        for i in 1..=10 {
            println!("{}", i);
            thread::sleep(Duration::from_millis(1000));
            total += i;
        }
        println!("Total: {}", total);
    }

    Burada iki thread de thread_proc içerisindeki yerel değişkenlerin farklı kopyalarını kullanmaktadır. 
---------------------------------------------------------------------------------------------------------------------------*/

/*---------------------------------------------------------------------------------------------------------------------------
    Çok sayıda threda oluşturup onların hepsini nasıl join edebiliriz? Her spawn işlemindne elde edilen thread'e ilişkin 
    JoinHandle nesnesini ayrı bir dizide ya da Vec içerisinde tutmak gerekir. Örneğin:

    use std::thread;
    use std::time::Duration;

    fn main() {
        let mut jhs: Vec<_> = Vec::new();

        for i in 0..100 {
            jhs.push(thread::spawn(thread_proc));
        }

        for jh in jhs {
            jh.join().unwrap();
        }
    }

    fn thread_proc() {
        println!("thread_proc running");
        thread::sleep(Duration::from_millis(1000));
    }

    Bunu biraz daha pratik bir biçimde şöyle de yapabilirdik:

    use std::thread;
    use std::time::Duration;

    fn main() {
        let jhs: Vec<_> = (0..10).map(|_| {
        thread::spawn(thread_proc)
        }).collect();

        for jh in jhs {
            jh.join().unwrap();
        }
    }

    fn thread_proc() {
        println!("thread_proc running");
        thread::sleep(Duration::from_millis(1000));
